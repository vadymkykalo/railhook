Transform Studio answers two questions before a transformation ever touches a delivery: *what does this template turn my payload into*, and *what exactly would my endpoint receive*. Nothing is sent and nothing is stored, so you can run it against a production template as often as you like.

It is **Develop → Transform Studio** in the dashboard, and two endpoints under the API — `POST /api/v1/projects/{projectId}/transform-preview` and `POST /api/v1/projects/{projectId}/transform-preview/delivery-dry-run`. See [API reference](/docs/api-reference/) for their request and response shapes.

## Two modes

| Mode | What it answers | What it needs |
|---|---|---|
| **Preview** | What the template produces from this payload. | An input payload, and a saved transformation or a template. |
| **Dry run** | What the HTTP request to a given endpoint would look like — body, headers and signature. | The same, plus an endpoint. |

Preview never touches an endpoint, so it needs nothing beyond read access. A dry run returns a **valid signature** computed with the endpoint's real signing secret, which is enough to mint a body that endpoint will accept as genuine — so it requires write access and a `READ_WRITE` API key. See [Authentication](/docs/platform/authentication/).

## Preview a template

<Steps>

1. **Put a payload in.** Either paste one, or press **Load Event** and pick a real event from the project — the payload as your application sent it, which is the one that finds the mistakes a hand-written sample never does.

2. **Choose what to run.** Pick a saved transformation, or write a template into the expression box:

   - A box that starts with `{` or `[` is treated as a **JSON template**, the same `${$.path}` template a transformation carries. See [Transformations](/docs/outgoing/transformations/#the-template).
   - Anything else is treated as a **single extraction**, such as `$.data` — the same simple form a destination's `payloadTransform` takes.
   - Empty is pass-through: the payload is returned formatted and unchanged.

3. **Run it.** The output panel shows the result, whether it differs from the input at all, and any errors. An extraction that matched nothing says so and returns `null`, because a path that matches nothing is not an error in a template and the studio is where you want to notice it anyway.

</Steps>

<Aside type="tip" title="The expression box is not full JSONPath">
A single extraction is resolved as a plain path into the document: `$.data.customer` reaches that object, and `$` returns the whole payload. Filters, wildcards and array predicates belong in a JSON template, where every `${…}` is evaluated as JSONPath proper.
</Aside>

## Dry-run a delivery

Switch the mode to **Dry run** and pick a target endpoint. The result is the request that endpoint would have received:

- the transformed body,
- the headers, including any custom headers you added,
- the `X-Signature` over that body, computed with the endpoint's current signing secret,
- the endpoint's URL, and the name and version of the transformation that was applied.

Nothing is sent. A disabled endpoint is dry-run all the same, with a warning saying so — which is usually what you want, since a disabled endpoint is often one you are in the middle of fixing.

## What it cannot do

This is the honest list, and each line is something people expect it to do.

- **It cannot save.** There is no "save to transformation" in the studio. Create or edit the transformation on the Transformations page or through the API, then select it here. What you type into the expression box is a scratch template and disappears with the page.
- **It does not work out which transformation a real delivery would pick.** It applies the one you name. Subscription settings and [rules](/docs/outgoing/rules/) are not consulted, so a rule that would override the transformation for matching events is invisible here.
- **A dry run is not a byte-for-byte rehearsal of the request.** A real delivery also carries `X-Event-Id`, `X-Delivery-Id`, `X-Sequence-Number` and `Idempotency-Key`, none of which exist until there is a delivery to give them values. Use it to check the body and the signing secret, not to predict every header.
- **The signature is always the `t=…,v1=…` form.** An endpoint set to the Standard Webhooks scheme is signed with `webhook-id`, `webhook-timestamp` and `webhook-signature` instead, and the dry run does not produce those. See [Signatures](/docs/outgoing/signatures/).
- **Nothing is sent, so nothing is confirmed.** The dry run cannot tell you whether the endpoint accepts the body, only what it would be asked to accept. To make a real request, use the test console or send a test event.
- **The endpoint has to be in this project.** An endpoint id from a sibling project is reported as not found, deliberately: the same answer another organization's endpoint gets, so the dry run cannot be used to discover which ids exist.
