---
title: Receive GitLab webhooks reliably
description: Keep GitLab from disabling your webhook when your app is slow or down. Railhook checks X-Gitlab-Token, answers at once, and forwards to your service with retries and replay.
---
import { Steps, Aside } from '@astrojs/starlight/components';

GitLab sends its webhooks to a Railhook source. The source checks the secret token, stores each webhook as it arrived and forwards it to your service with retries. Railhook answers GitLab straight away, so a slow or down service no longer counts against the webhook.

## Why GitLab webhooks need a buffer

GitLab disables a webhook that keeps failing. After four consecutive failures it is disabled for one minute, growing to up to 24 hours as failures continue. After 40 consecutive failures it is disabled permanently and stays off. A webhook that times out can also be sent again as a duplicate. ([GitLab: Webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/))

A few bad deploys can switch your integration off unnoticed. With Railhook in front:

- GitLab's requests are answered as soon as they are stored, so they do not time out or fail because of your service.
- Your service gets up to 5 attempts per forward, with waits from 1 minute to 1 hour, and what still fails lands in **Failed Forwards**.
- A duplicate carrying the same `webhook-id` or `Idempotency-Key` header is answered with the stored copy and not forwarded again.

## Connect GitLab

You need a Railhook project and an API key. The same steps are available under **Incoming** in the dashboard.

```bash
export RAILHOOK_URL=https://railhook.io   # or your own instance
export RAILHOOK_API_KEY=...
export PROJECT_ID=...
```

<Steps>

1. **Choose a secret token.** With GitLab you pick it yourself:

   ```bash
   export GITLAB_WEBHOOK_TOKEN=$(openssl rand -hex 32)
   ```

2. **Create the source** with that token as the secret:

   ```bash
   curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/incoming-sources" \
     -H "X-API-Key: $RAILHOOK_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"name":"GitLab","providerType":"GITLAB","verificationMode":"PROVIDER","hmacSecret":"'"$GITLAB_WEBHOOK_TOKEN"'"}'
   ```

   Keep the `id` and the `ingressUrl` from the response.

3. **Add a destination**, the URL of your own service:

   ```bash
   curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/incoming-sources/$SOURCE_ID/destinations" \
     -H "X-API-Key: $RAILHOOK_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"url":"https://api.example.com/webhooks/gitlab","authType":"BEARER","authConfig":"{\"token\":\"...\"}","enabled":true}'
   ```

4. **Register the webhook in GitLab.** In the project or group, open **Settings → Webhooks** and add a new webhook. Paste the `ingressUrl` as the **URL**, the same token as the **Secret token**, and select the triggers you want.

5. **Send a test** with the webhook's **Test** button. It appears under **Incoming → Received**, with one forward per destination.

</Steps>

## How the token is checked

GitLab does not sign the body; it sends the secret token in the `X-Gitlab-Token` header. Railhook checks that the header equals the source's secret and answers `401`, storing nothing, when it does not. Because a token is not a signature, keep the ingress URL private and serve it over HTTPS.

<Aside type="note">
GitLab can also sign webhooks with a signing token. Railhook checks the secret token only, so use the **Secret token** field.
</Aside>

## What your service receives

The body exactly as GitLab sent it, byte for byte. Railhook passes GitLab's event headers through, `X-Gitlab-Event`, `X-Gitlab-Event-UUID` and `X-Gitlab-Instance`, so your service can tell a push from a merge request. `X-Gitlab-Token` is never forwarded: your service authenticates Railhook through the destination's credentials instead. See [Destinations](/docs/incoming/destinations/#what-the-destination-receives).

## Develop locally with the CLI

<Steps>

1. Install the CLI and log in, as in [CLI](/docs/tools/cli/), then open a tunnel to your app's port:

   ```bash
   railhook listen 3000
   ```

2. Add a second destination to the source with the printed public URL and your route appended, such as `https://<host>/tunnel/<slug>/webhooks/gitlab`. It reaches `http://localhost:3000/webhooks/gitlab`.

3. Click **Test** on the GitLab webhook, and the webhook arrives in your local app with its `X-Gitlab-Event` header. Disable that destination when you stop the tunnel.

</Steps>

## Replay after an outage

Each replayed webhook goes to every destination of the source as a new forward:

```bash
curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/incoming-events/bulk-replay" \
  -H "X-API-Key: $RAILHOOK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"sourceId":"'"$SOURCE_ID"'","from":"2026-09-18T10:00:00Z","to":"2026-09-18T14:00:00Z","verified":true}'
```

Replay reaches back as far as events are kept: 7 days on Railhook Cloud, and whatever you configure when self-hosting. Make your handler idempotent on what the webhook is about, such as the commit or merge request in the body, since a replay can send webhooks your service already processed. See [Replay](/docs/outgoing/replay/#replay-incoming-webhooks).
