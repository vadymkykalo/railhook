This guide puts Railhook between Square and your application. Square sends its event notifications to a Railhook source, which verifies the signature, stores each notification as it arrived and forwards it to your service with retries. Square only ever talks to Railhook, which answers straight away, so a slow or failing app stops being Square's problem — and stops being a reason for Square to turn your subscription off.

## Why Square webhooks need a buffer

Square expects a `2xx`, and treats a response that takes longer than 10 seconds as a failure. It then retries with exponential backoff for up to 24 hours, adding `square-retry-number` and `square-retry-reason` headers as it goes. If a subscription fails to return a single `2xx` for three weeks, Square warns by email and then disables it. ([Square: Webhooks overview](https://developer.squareup.com/docs/webhooks/overview))

With Railhook in front:

- Square is answered as soon as the notification is stored, well inside the 10 seconds.
- Your service gets up to 5 attempts per forward, with waits from 1 minute to 1 hour, and what still fails lands in **Failed Forwards**.
- A retried notification with the same `event_id` is answered with the stored copy and not forwarded twice.
- Anything stored can be replayed long after Square's 24 hours are up.

## Connect Square

You need a Railhook project and an API key. Everything below can also be done under **Incoming** in the dashboard.

```bash
export RAILHOOK_URL=https://railhook.io   # or your own instance
export RAILHOOK_API_KEY=...
export PROJECT_ID=...
```

<Steps>

1. **Create the source.** Leave the secret empty for a moment — Square only shows you the signature key once the subscription exists:

   ```bash
   curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/incoming-sources" \
     -H "X-API-Key: $RAILHOOK_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"name":"Square","providerType":"SQUARE","verificationMode":"NONE"}'
   ```

   Keep the `id` and the `ingressUrl` from the response.

2. **Subscribe in the Square Developer Console.** Open your application, go to **Webhooks → Subscriptions**, choose **Sandbox** or **Production** at the top of the page — the two keep separate subscriptions — and click **Add subscription**. Paste the `ingressUrl` exactly as the source shows it as the notification URL, and select the event types you want. ([Square: Subscribe to event notifications](https://developer.squareup.com/docs/webhooks/step2subscribe))

3. **Copy the signature key.** Open the subscription's endpoint details and click **Show** next to **Signature Key**. That key is what Square signs with.

4. **Give Railhook the key and turn verification on:**

   ```bash
   curl -X PUT "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/incoming-sources/$SOURCE_ID" \
     -H "X-API-Key: $RAILHOOK_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"name":"Square","verificationMode":"PROVIDER","hmacSecret":"'"$SQUARE_SIGNATURE_KEY"'"}'
   ```

   `name` is required on an update; everything else you leave out keeps its current value.

5. **Add a destination**, the URL of your own service:

   ```bash
   curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/incoming-sources/$SOURCE_ID/destinations" \
     -H "X-API-Key: $RAILHOOK_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"url":"https://api.example.com/webhooks/square","authType":"BEARER","authConfig":"{\"token\":\"...\"}","enabled":true}'
   ```

6. **Send a test event** from the subscription's page in the Developer Console. It appears under **Incoming → Received**, with one forward per destination.

</Steps>

## How the signature is checked

Square's `x-square-hmacsha256-signature` is a base64 HMAC-SHA256 over the **notification URL followed immediately by the raw body**, with no separator, keyed with the signature key. Railhook computes the same thing and compares it in constant time. A request that does not match is answered `401` and is not stored.

<Aside type="caution" title="The URL is part of the signature">
This is the thing that breaks Square verification, every time. `http` where Square has `https`, a trailing slash, a different host — any of them changes the digest and every genuine notification fails. Railhook rebuilds the URL from its configured public address rather than from the incoming request, so a reverse proxy cannot corrupt it. On a self-hosted instance that address is `APP_BASE_URL`, which the installer sets from `--domain`, or `TUNNEL_INGRESS_BASE_URL` when webhooks arrive on a different host. Paste into Square exactly the ingress URL the source shows, character for character.
</Aside>

Square's scheme carries no timestamp, so an unchanged body always produces the same signature. What separates Square's own retry from a replay is the notification's `event_id`, which Square documents as an idempotency value: Railhook stores it, and a second notification carrying one it already has is answered with the stored event instead of being forwarded again.

## What your service receives

The body exactly as Square sent it, byte for byte, with Square's own headers passed through — including `square-environment`, which tells you whether the notification came from Sandbox or Production. `x-square-hmacsha256-signature` is not forwarded: your service authenticates Railhook through the destination's credentials and has no use for the signature key. See [Destinations](/docs/incoming/destinations/#what-the-destination-receives).

## Develop locally with the CLI

<Steps>

1. Install the CLI and log in, as in [CLI](/docs/tools/cli/), then open a tunnel to your app's port:

   ```bash
   railhook listen 3000
   ```

2. Add a second destination to the source with the printed public URL and your route appended, such as `https://<host>/tunnel/<slug>/webhooks/square`. It reaches `http://localhost:3000/webhooks/square`.

3. Take a payment in the Sandbox, or send a test event, and it arrives in your local app. Disable that destination when you stop the tunnel.

</Steps>

<Aside type="tip" title="Sandbox and Production are two sources">
Square keeps separate subscriptions per environment, and each has its own signature key. Give each one its own Railhook source, so a sandbox key can never verify a production notification — and so `square-environment` and your source name agree.
</Aside>

## Replay after an outage

Replay what arrived while your service was down. Each replayed notification goes to every destination of the source as a new forward:

```bash
curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/incoming-events/bulk-replay" \
  -H "X-API-Key: $RAILHOOK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"sourceId":"'"$SOURCE_ID"'","from":"2026-09-18T10:00:00Z","to":"2026-09-18T14:00:00Z","verified":true}'
```

Replay reaches back as far as events are kept: 7 days on Railhook Cloud, and whatever you configure when self-hosting. Keep your handler idempotent on `event_id`, since a replay can send notifications your service already processed. See [Replay](/docs/outgoing/replay/#replay-incoming-webhooks).
