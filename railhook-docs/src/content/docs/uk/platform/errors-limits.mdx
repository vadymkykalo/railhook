Усі помилки API Railhook мають однакову структуру, тож одного обробника у вашому клієнті вистачить для всіх.

## Формат помилки

```json title="400 Bad Request"
{
  "error": "validation_error",
  "message": "Invalid request parameters",
  "status": 400,
  "fieldErrors": {
    "type": "Event type is required",
    "data": "Event data cannot be empty"
  }
}
```

| Поле | Завжди є | Що означає |
|---|---|---|
| `error` | Так | Незмінний машиночитний код. Саме за ним розрізняйте помилки в коді. |
| `message` | Так | Пояснення для людини. Не розбирайте його програмно. |
| `status` | Так | HTTP-статус, продубльований у тілі |
| `fieldErrors` | Ні | У помилках валідації: назва поля → що з ним не так |

## Коди помилок

| Статус | `error` | Що робити |
|---|---|---|
| `400` | `validation_error` | Виправте поля, перелічені в `fieldErrors`. |
| `400` | `malformed_request` | Тіла немає або воно не є коректним JSON. |
| `400` | `missing_parameter`, `invalid_parameter` | Параметра запиту чи шляху немає або він має неправильний формат. |
| `400` | `invalid_url` | URL відхилено, наприклад, захистом від SSRF. |
| `400` | `invalid_request` | Запит зрозуміло, але відхилено, наприклад, подію, яка розгалузилася б понад ліміт. Прочитайте `message`. |
| `401` | `unauthorized` | Облікових даних немає, вони прострочені або неправильні. Оновіть токен доступу або перевірте заголовок `X-API-Key`. |
| `403` | `forbidden` | Автентифікацію пройдено, але роль чи рівень доступу ключа цього не дозволяє. Ключ `READ_ONLY` не може нічого змінювати. |
| `404` | `not_found` | У вашій організації немає нічого з таким ідентифікатором. |
| `405` | `method_not_allowed` | Неправильний HTTP-метод. Правильні перелічено в заголовку `Allow`. |
| `409` | `conflict` | Таке вже існує або змінилося, поки ви редагували. Отримайте актуальну версію й спробуйте ще раз. |
| `413` | `payload_too_large` | Тіло перевищує ліміт розміру. |
| `415` | `unsupported_media_type` | Надсилайте `Content-Type: application/json`. |
| `422` | `unprocessable_entity` | Запит коректний, але в поточному стані ресурсу його не можна застосувати. |
| `429` | `rate_limit_exceeded`, `organization_rate_limit`, `platform_rate_limit` | Зачекайте стільки секунд, скільки вказано в `Retry-After`, і повторіть запит. |
| `500` | `internal_error` | Збій на боці Railhook. Повторіть запит з експоненційною затримкою. |

Деякі помилки мають у тому самому форматі лише загальний код (`client_error` для `4xx` або `server_error` для `5xx`), наприклад, перевищення ліміту спроб входу чи заблокована зміна останнього власника. Тож спершу перевіряйте `status`, а `error` використовуйте для уточнення.

<Aside type="tip" title="Після яких помилок повторювати запит">
Повторюйте запити після `429` і `5xx`, збільшуючи затримку між спробами. Ніколи не повторюйте без змін запит, що отримав іншу `4xx`: він завершиться тією самою помилкою. Надсилання подій безпечно повторювати, якщо ви передаєте заголовок `Idempotency-Key`: з тим самим ключем друга подія не створюється.
</Aside>

## Ліміти частоти запитів

Це типові значення для розгортання на власному сервері. У Railhook Cloud свої ліміти, [описані нижче](#ліміти-railhook-cloud).

| Ліміт | Що обмежує | Типово | Відповідь 429 |
|---|---|---|---|
| Приймання подій | `POST /api/v1/events`, для кожного проєкту | 100 на секунду | `rate_limit_exceeded` із заголовками залишку ліміту |
| Організація | Увесь API-трафік однієї організації | Вимкнено (`ORG_RATE_LIMIT_ENABLED=false`); 200 на секунду, якщо ввімкнено | `organization_rate_limit`, `Retry-After: 1` |
| Платформа | Увесь трафік, для кожного інстансу API | 5000 на секунду (`GLOBAL_RATE_LIMIT_PER_SECOND`) | `platform_rate_limit` |
| Ingress-адреса | Вебхуки, отримані на `/ingress/…`, для кожного джерела | 100 на секунду (`WEBHOOK_INCOMING_RATE_LIMIT_PER_SECOND`), якщо джерело не задає власного ліміту | `Retry-After: 1` |
| Вхід | Для кожної IP-адреси і кожного email | 10 на хвилину (`AUTH_RATE_LIMIT_LOGIN_PER_MINUTE`) | `429` |
| Оновлення сесії | Для кожного токена оновлення і кожної IP-адреси | 30 на хвилину на токен (`AUTH_RATE_LIMIT_REFRESH_PER_TOKEN_PER_MINUTE`), 600 на хвилину на IP-адресу (`AUTH_RATE_LIMIT_REFRESH_PER_IP_PER_MINUTE`) | `429` |

Кожна відповідь на `POST /api/v1/events` містить поточний залишок ліміту проєкту:

| Заголовок | Що означає |
|---|---|
| `X-RateLimit-Limit` | Скільки запитів дозволено в поточному вікні |
| `X-RateLimit-Remaining` | Скільки з них лишилося |
| `X-RateLimit-Reset` | Unix-час, коли почнеться нове вікно |
| `Retry-After` | Лише у відповіді `429`: скільки секунд чекати |

## Ліміти Railhook Cloud

У Railhook Cloud на railhook.io кожна організація працює на тарифі Free. Доступні всі функції, зокрема воркфлоу, правила, відтворення і mTLS; обмежено лише обсяги. Ці ліміти діють замість наведених вище типових значень для власного сервера:

| Ліміт | Тариф Free |
|---|---|
| Приймання подій (`POST /api/v1/events`) | 10 на секунду для кожного проєкту |
| Події | 10 000 на місяць |
| Проєкти | 3 |
| Ендпоінти | 5 на проєкт |
| Учасники | 5 на організацію |
| Зберігання подій | 7 днів |
| Активні тунелі | 1 |
| Доставок на подію (розгалуження) | 100 |

На власному сервері тарифних лімітів немає. Діють лише типові значення з таблиць на цій сторінці.

## Ліміти розміру та розгалуження

| Ліміт | Типово | Змінна |
|---|---|---|
| Тіло запиту до API | 256 КБ (262144 байти) | `WEBHOOK_MAX_PAYLOAD_SIZE_BYTES` |
| Тіло запиту на ingress-адресу | 512 КБ (524288 байтів) | `WEBHOOK_INCOMING_MAX_PAYLOAD_SIZE_BYTES` |
| Доставок на подію (розгалуження) | 50 на власному сервері | — |

Для ingress-адреси ліміт вищий, бо розмір того, що надсилає провайдер, від вас не залежить. Подію, яка збігається з більшою кількістю підписок, ніж дозволяє ліміт розгалуження, відхиляють повністю з `400`. Не буває так, щоб її доставили на частину відповідних ендпоінтів, а на решту ні.

## Відповіді ingress-адреси

Ingress-адреса відповідає не вам, а провайдеру, який надіслав вебхук, тому її відповіді коротші: успішне отримання — це `202` із `status` і `requestId`, а помилка містить `error` і `message` без `status`. Коли в розгортанні з тарифами вичерпано квоту, ingress-адреса відповідає `429` з `Retry-After: 3600` і без подробиць, тож провайдер нічого не дізнається про ваш тариф.
