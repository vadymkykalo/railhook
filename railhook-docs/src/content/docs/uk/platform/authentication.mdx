Railhook приймає чотири види облікових даних. Ця сторінка пояснює, який із них використовувати, як його отримати і як замінити, не зламавши тих, хто ним користується.

| Облікові дані | Хто використовує | Як передаються | Що несуть |
|---|---|---|---|
| Токен доступу (JWT) | Панель і все, що діє від імені людини | `Authorization: Bearer …` | Користувача, його організацію, його роль |
| API-ключ | Ваші сервери та SDK | `X-API-Key: …` | Один проєкт і область дії |
| Код пристрою | `railhook login` у CLI | Обмінюється на сесію | Те саме, що токен доступу |
| Токен адміністратора платформи | Той, хто експлуатує розгортання | `X-Platform-Admin-Token: …` | Доступ до `/api/v1/admin/**` у всіх організаціях |

## Токени доступу

Увійдіть через `POST /api/v1/auth/login`. Тіло відповіді містить `accessToken`. Токена оновлення в тілі немає: його встановлено як `HttpOnly`-cookie з назвою `refresh_token` і шляхом `/api/v1/auth`.

<Tabs syncKey="lang">
  <TabItem label="cURL">
    ```bash
    curl -X POST https://railhook.example.com/api/v1/auth/login \
      -H "Content-Type: application/json" \
      -c cookies.txt \
      -d '{"email":"you@company.com","password":"••••••••"}'
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    const res = await fetch('https://railhook.example.com/api/v1/auth/login', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ email: 'you@company.com', password: process.env.PASSWORD }),
    });
    const { accessToken } = await res.json();
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import os

    import requests

    res = requests.post(
        "https://railhook.example.com/api/v1/auth/login",
        json={"email": "you@company.com", "password": os.environ["PASSWORD"]},
    )
    access_token = res.json()["accessToken"]
    ```
  </TabItem>
</Tabs>

Передавайте токен доступу в кожному запиті, що діє від імені цього користувача:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

### Час життя та оновлення

| Токен | Час життя за замовчуванням |
|---|---|
| Токен доступу | 15 хвилин |
| Токен оновлення | 24 години |

`POST /api/v1/auth/refresh` читає cookie `refresh_token`, а якщо cookie немає — поле `refreshToken` у JSON-тілі. Він повертає новий токен доступу й встановлює нове cookie оновлення. Витрачений токен оновлення потрапляє до чорного списку. Панель повторює оновлення, що впало з `429` або `5xx`, і виходить із сесії, лише коли саму сесію відхилено.

<Aside type="caution" title="Повторно використаний токен оновлення завершує всі сесії">
Якщо пред'явити вже витрачений токен оновлення, Railhook відкликає всі токени цього користувача. Саме так виглядає викрадений токен, тож до нього так і ставляться.
</Aside>

Кожен вхід — це сесія. Користувач може переглянути свої сесії, закрити одну або закрити всі. `POST /api/v1/auth/logout` відкликає поточні токени доступу та оновлення.

### Невдалі входи

Вхід обмежено за частотою, а повторні невдачі на якийсь час блокують обліковий запис. Обидва механізми налаштовуються через змінні середовища:

| Змінна | За замовчуванням | Значення |
|---|---|---|
| `AUTH_RATE_LIMIT_LOGIN_PER_MINUTE` | `10` | Спроб входу на IP і на email за хвилину. Понад це API відповідає `429`. |
| `AUTH_RATE_LIMIT_REFRESH_PER_TOKEN_PER_MINUTE` | `30` | Оновлень сесії на один токен оновлення за хвилину. Оновлення має власний бюджет і не витрачає бюджет входу. |
| `AUTH_RATE_LIMIT_REFRESH_PER_IP_PER_MINUTE` | `600` | Оновлень сесії на IP за хвилину |
| `AUTH_LOCKOUT_ENABLED` | `true` | Вмикає або вимикає блокування |
| `AUTH_LOCKOUT_THRESHOLD` | `5` | Невдач поспіль до першого блокування |
| `AUTH_LOCKOUT_INITIAL_SECONDS` | `60` | Перше блокування. Подвоюється з кожною наступною невдачею. |
| `AUTH_LOCKOUT_MAX_SECONDS` | `900` | Найдовше блокування |
| `AUTH_LOCKOUT_FAILURE_WINDOW_MINUTES` | `60` | За який період рахуються невдачі |

Блокування спливає саме, а скидання пароля знімає його одразу.

## API-ключі

API-ключ належить одному проєкту. Ним надсилають події, і на ньому побудовані SDK.

<Steps>
1. Створіть ключ для проєкту в панелі або через `POST /api/v1/projects/{projectId}/api-keys`.
2. Скопіюйте `key` з відповіді. Його показують один раз: Railhook зберігає лише хеш, тож загублений ключ не відновити, лише замінити.
3. Покладіть його у змінну середовища на сервері, який ви контролюєте, і передавайте в заголовку `X-API-Key`:

   ```http
   X-API-Key: Kz1uAIM8VeJUQN7yGSYCst64WxNLabBHfOYbrPlJ1yk
   ```
</Steps>

### Області дії та строк

| Область дії | Дозволяє |
|---|---|
| `READ_WRITE` | Читання й запис. Надсилання події — це запис. За замовчуванням. |
| `READ_ONLY` | Лише читання. Запис відповідає `403`. |

Ключ може мати дату `expiresAt`. Після неї, або коли ключ відкликано, він більше нічого не автентифікує. Відкликання діє негайно, без пільгового періоду.

<Aside type="danger">
Ключ у клієнтському коді чи в репозиторії може використати будь-хто, хто його прочитає. Тримайте ключі лише на серверах.
</Aside>

### Ротація ключа без простою

`POST /api/v1/projects/{projectId}/api-keys/{apiKeyId}/rotate` створює заміну з тією самою назвою та областю дії. Старий ключ працює ще впродовж пільгового вікна, тож ви встигнете розгорнути новий усюди, перш ніж старий перестане діяти.

| Поле | За замовчуванням | Значення |
|---|---|---|
| `gracePeriodHours` | `24` | Скільки ще працює старий ключ. `0` відрізає його одразу — таку ротацію роблять після витоку. |
| `expiresAt` | немає | Необов'язковий строк дії нового ключа |

Ротація ніколи не подовжує старий ключ: якщо він мав спливти раніше, ця дата лишається. Ключ можна ротувати один раз. Щоб ротувати знову, ротуйте його заміну.

## Вхід у CLI

`railhook login` використовує код пристрою. CLI показує URL і код, ви підтверджуєте код у панелі, і CLI отримує власну сесію. Див. [CLI](/docs/uk/tools/cli/).

## Токен адміністратора платформи

`PLATFORM_ADMIN_TOKEN` — облікові дані для операторських ендпоінтів `/api/v1/admin/**`. Він не залежить від організацій: `OWNER` організації його не має. Залиште змінну порожньою, і адмінські ендпоінти лишаться недоступними. Встановлюйте її лише тоді, коли оператору вони потрібні, і передавайте токен у заголовку `X-Platform-Admin-Token`.

Форми запитів і відповідей для кожного ендпоінта автентифікації — у [довіднику API](/docs/uk/api-reference/).

## Зміна адреси email

Відкрийте **Налаштування → Профіль → Змінити email**. Що станеться, залежить від того, чи підтвердив обліковий запис свою поточну адресу.

- **Ще не підтверджено.** Адреса змінюється одразу, і на неї йде нове посилання для підтвердження. Посилання, надіслане на стару адресу, перестає працювати. Обліковий запис лишається непідтвердженим, з тими самими обмеженнями, доки нову адресу не підтверджено. Якщо розгортання має CAPTCHA, зміна її запитує, як і реєстрація. Банер, що просить підтвердити пошту, пропонує ту саму форму під **Помилилися в адресі? Змініть її**.
- **Підтверджено.** Введіть пароль. Обліковий запис, що входить лише через Google, пароля не має: увійдіть через Google ще раз і змініть адресу протягом 10 хвилин. Нічого не змінюється, доки хтось не відкриє посилання, надіслане на нову адресу. Стара адреса отримує сповіщення з посиланням **Це був не я**, яке скасовує зміну. До того часу Налаштування показують адресу, що чекає на підтвердження, з кнопками **Надіслати посилання ще раз** і **Скасувати зміну**.

Підтвердження зміни або її скасування зі старої адреси завершує всі сесії. Посилання працюють один раз і спливають за 24 години. Адресу, яка вже належить обліковому запису, відхиляють з тією самою відповіддю, що й під час реєстрації. `EMAIL_SUPPORT_ADDRESS` задає контакт, який дає сповіщення на стару адресу; див. [довідник конфігурації](/docs/uk/self-hosting/configuration/).

<Aside type="caution" title="Денні ліміти">
Обліковий запис може змінити адресу 3 рази на день і отримати 5 листів для підтвердження на день — разом для реєстрації, повторного надсилання і зміни.
</Aside>

Організація, її план і використання лишаються як були, а прив'язаний обліковий запис Google лишається прив'язаним. Кожен запит, підтвердження, скасування і досягнутий ліміт записуються до журналу аудиту кожної організації, до якої належить людина, тож власник бачить зміну адреси учасника.

Адреси email не залежать від регістру: `Ada@Company.com` і `ada@company.com` — це той самий обліковий запис для реєстрації, входу, запрошень, скидання пароля, зміни email і входу через Google. Адреси зберігаються в нижньому регістрі.

Реєстрація, запрошення учасників і email для рахунків відхиляють адресу, закінчення якої не може отримувати пошту, як-от `gmail.con`, і пропонують адресу, яку, найімовірніше, мали на увазі.

## Вхід через Google

Кнопка «Продовжити з Google» з'являється на сторінках входу й реєстрації, щойно розгортання має OAuth-клієнт Google. Одна кнопка робить обидві речі:

- Для облікового запису Google, якому не відповідає жоден обліковий запис Railhook, він створюється одразу: адреса позначена підтвердженою, і є власна організація. Для Google Workspace організація називається за доменом (`acme.com` стає **Acme**), для особистого облікового запису — **«Ім'я»'s workspace**. Назву можна змінити в налаштуваннях організації.
- Обліковий запис, зареєстрований з паролем на ту саму адресу, отримує Google як другий спосіб входу. Пароль і далі працює.
- Відповідність шукається за постійним ідентифікатором людини в Google, тож зміна адреси в обліковому записі Google веде до того самого облікового запису Railhook.

Обліковий запис, створений через Google, не має пароля. Щоб додати його, скористайтеся **«Забули пароль?»** на сторінці входу.

<Steps>

1. У [Google Cloud Console](https://console.cloud.google.com/apis/credentials) створіть **OAuth client ID** типу **Web application**.

2. Додайте дозволений redirect URI. Це ваш `APP_BASE_URL` плюс шлях callback, і він має збігатися точно:

   ```text
   https://railhook.example.com/api/v1/auth/oauth/google/callback
   ```

   Для локального стеку на порту 8080 додайте також `http://localhost:8080/api/v1/auth/oauth/google/callback`.

3. На **OAuth consent screen** залиште лише області `openid`, `email` і `profile`.

4. Задайте обидва значення для API і перезапустіть його:

   ```bash
   GOOGLE_OAUTH_CLIENT_ID=1234567890-abc.apps.googleusercontent.com
   GOOGLE_OAUTH_CLIENT_SECRET=GOCSPX-...
   ```

   У Kubernetes задайте `googleSignIn.clientId`, а секрет покладіть у Secret, названий у `googleSignIn.existingSecret`.

</Steps>

<Aside type="note">
Браузер ніколи не бачить токен в URL. Після Google API перенаправляє на дашборд з одноразовим кодом, який діє один раз протягом 60 секунд, і дашборд обмінює його на сесію через `POST /api/v1/auth/oauth/exchange`.
</Aside>
