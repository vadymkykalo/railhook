Клієнти, чиї приймачі стоять за брандмауером, питають, з якої IP-адреси приходять ваші вебхуки. На цій сторінці описано, як дати їм фіксовану адресу.

Окремого налаштування для цього в Railhook немає. HTTP-клієнт воркера не має параметра для forward-проксі й не читає `HTTP_PROXY` чи `HTTPS_PROXY`. Тож розв'язуйте задачу рівнем нижче: доставки надсилає лише **воркер**, тому, зафіксувавши його вихідну адресу, ви фіксуєте її для кожного вебхука, який надсилаєте.

```text
worker  →  your network's outbound address  →  your customer's endpoint
                        ↑
            this is the address they allowlist
```

Типово ця адреса — та, яку випадково використовує ваша інфраструктура: публічна IP-адреса вузла, спільний пул NAT чи адреса, що змінюється, коли вузол замінюють. Жодну з них не можна внести до списку дозволених.

## Варіант 1: NAT-шлюз зі статичною IP-адресою

Розмістіть підмережу воркера за керованим NAT-шлюзом зі статичною адресою. Тоді всі вихідні з'єднання йтимуть із цієї адреси. Почніть саме з цього варіанта: він не потребує жодних налаштувань Railhook і переживає заміну вузлів.

| Середовище | Сервіс | Що прикріпити |
|---|---|---|
| AWS | NAT Gateway | Elastic IP — у таблиці маршрутів приватної підмережі, де працюють вузли воркера |
| Google Cloud | Cloud NAT | Зарезервовану статичну зовнішню IP-адресу |
| Azure | NAT Gateway | Статичну публічну IP-адресу |
| Інші провайдери, bare metal | Хост-шлюз | Плаваючу IP-адресу; типовий маршрут воркера має йти через цей хост |

<Aside type="tip" title="Опублікуйте дві адреси">
Один NAT-шлюз — це єдина точка відмови. Клієнтам набагато простіше внести другу адресу до списку дозволених заздалегідь, ніж посеред збою.
</Aside>

## Варіант 2: окремий пул вузлів

Якщо фіксовану адресу має використовувати лише трафік вебхуків, запускайте воркер на вузлах за NAT, а інші навантаження тримайте деінде. Тоді трафік панелі керування, резервні копії й завантаження образів не йтимуть через адресу, яка може бути дорогою чи мати ліміти.

<Aside type="caution">
У Helm-чарті `nodeSelector` і `tolerations` — це спільні значення верхнього рівня, які застосовуються і до API, і до воркера. Щоб розмістити окремо лише воркер, змініть його deployment патчем або задайте для нього окреме перевизначення значень.
</Aside>

## Варіант 3: вихідний шлюз

Якщо у вас уже є service mesh або вихідний шлюз, як-от egress gateway в Istio чи Cilium, спрямуйте трафік воркера через нього. Перенаправлення відбувається нижче рівня застосунку, тому й працює без жодного налаштування Railhook.

Вихідний шлюз — ще й зручне місце, щоб записувати в журнал або обмежувати, куди йдуть доставки. Він доповнює власний захист Railhook від SSRF, але не замінює його: Railhook перевіряє кожен URL доставки ще до того, як сформує запит, і відхиляє приватні адреси, якщо їх не дозволено через `WEBHOOK_ALLOW_PRIVATE_IPS` або `WEBHOOK_ALLOWED_HOSTS`.

## Що повідомити клієнтам

Опублікуйте адреси там, де клієнти зможуть знайти їх, не звертаючись до вас, і вкажіть:

1. **Усі адреси**, які можуть використовуватися.
2. **Що список може змінитися — і за скільки часу ви попередите.** Список дозволених, змінений без попередження, — це збій на чужій інфраструктурі.

Усе це стосується лише вебхуків, які надсилаєте ви. Провайдерам, що надсилають вебхуки **до** Railhook, потрібна ваша адреса для вхідних вебхуків, а не список дозволених.
