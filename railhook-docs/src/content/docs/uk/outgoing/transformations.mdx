Трансформація перетворює вміст події на тіло запиту, якого очікує конкретний отримувач. Збережена подія лишається незмінною; змінюється лише тіло доставки.

## Два види

Кожна трансформація має вид, `kind`, і саме він вирішує, як прочитати збережений текст.

| `kind` | Що це | Коли брати |
|---|---|---|
| `TEMPLATE` | JSON-документ, рядкові значення якого можуть містити вирази `${$.jsonpath}`. Типовий вид і те, чим була кожна трансформація до появи JavaScript. | Отримувачу потрібні ті самі поля під іншими назвами або лише частина з них. Шаблон декларативний, не вміє циклів і не підносить несподіванок. |
| `JAVASCRIPT` | Одна функція `function handler(webhook)`, яка повертає тіло запиту й виконується в пісочниці. | Структуру треба обчислити: пройти масив, додати поле залежно від значення, відформатувати дату, скасувати доставку. |

Якщо `kind` не задано, це `TEMPLATE`. Усі трансформації, які існували до появи цього поля, — шаблони, і нічого не мігрує: шаблон, який працює, не треба «виправляти».

## Шаблон

Трансформація виду `TEMPLATE` — це JSON-документ, рядкові значення якого можуть містити JSONPath-вирази в плейсхолдерах `${…}`. Плейсхолдери обчислюються за вмістом події; усе інше копіюється як є.

```json title="Шаблон"
{
  "id": "${$.orderId}",
  "customer": {
    "email": "${$.customer.email}",
    "plan": "${$.subscription.plan_name}"
  },
  "amount_cents": "${$.amount}",
  "note": "Order ${$.orderId} from Railhook"
}
```

| Як записано | Результат |
|---|---|
| Рядок, що складається рівно з одного виразу, `"${$.amount}"` | Значення, на яке вказує вираз, зі своїм типом: число лишається числом, об'єкт — об'єктом. |
| Вираз усередині іншого тексту, `"Order ${$.orderId} from Railhook"` | Рядок із підставленим значенням. |
| Шлях, який нічого не знаходить | `null`, якщо вираз займає все значення, і текст `null` усередині довшого рядка. Це не помилка. |

<Aside type="caution" title="Одруківка в шляху минає непоміченою">
Шлях, який нічого не знаходить, не ламає шаблон, тож необов'язкове поле лишається необов'язковим. Через те саме правило шлях з одруківкою мовчки дає `null`. Перш ніж підключати шаблон, перевірте його на реальному вмісті події.
</Aside>

Шаблон — це не скрипт. Він може прочитати вміст і переставити в ньому поля, але не вміє ні циклів, ні розгалужень, ні зовнішніх викликів, ні обчислень. Саме для цього є другий вид.

## Контракт JavaScript

Трансформація виду `JAVASCRIPT` — це один файл, який визначає одну функцію:

```js title="Вигляд будь-якого скрипта"
function handler(webhook) {
  return { payload: { id: webhook.eventId } };
}
```

`handler` — єдина назва, яку викликає Railhook. Усе інше у файлі — допоміжні функції, константи — ваше і виконується перед нею. Підійде будь-який запис, після якого `handler` є функцією, зокрема `const handler = (webhook) => ({ payload: webhook.payload });`.

Це обіцянка, яку ми маємо намір дотримати: скрипти пишуть під ці назви, тож розширення переліку — це зміна контракту, а не дрібне доопрацювання.

### Що є у `webhook`

| Властивість | Що це |
|---|---|
| `payload` | Вміст події, уже розібраний. Об'єкт, масив або те, чим було тіло події. |
| `eventType` | Тип події, а для вхідного вебхука — тип події сервісу. |
| `eventId` | Ідентифікатор події. |
| `timestamp` | Коли подію було оголошено, рядком у форматі ISO-8601. |
| `direction` | `OUTGOING` для доставки, `INCOMING` для пересилання. |
| `url` | Адреса ендпоінта або призначення, на яку націлена ця спроба. Лише для читання. |
| `headers` | Власні заголовки, налаштовані на ендпоінті чи призначенні, куди йде ця спроба, — не заголовки самого Railhook і не готовий запит. Підпис, ідентифікатори й порядковий номер обчислюються вже після того, як скрипт відпрацював, і їх свідомо не показують: скрипт, який міг би прочитати підпис, — це скрипт, який міг би його злити. У попередньому перегляді це ті `customHeaders`, які ви надіслали. |
| `attemptNumber` | Котра це спроба, `1` для першої. Саме цього потребує підказка для ідемпотентності або рядок, який пишуть у лог лише на повторі, — і сам скрипт цього не обчислить. У попередньому перегляді — `null`, бо спроби немає. |

Цей перелік — увесь світ скрипта. Більше дотягнутися нема до чого.

### Що функція має повернути

| Що повернути | Дія |
|---|---|
| `{ payload: … }` | `payload` серіалізується в JSON і стає тілом запиту, яке підписують і надсилають. |
| `{ payload: …, headers: { … } }` | Ці заголовки додають до запиту. Значення зводяться до рядка; `null` і вкладений об'єкт відкидаються. |
| `{ cancel: true, cancelReason: '…' }` | Нічого не надсилається, доставка завершується. Див. [Коли скрипт скасовує доставку](#коли-скрипт-скасовує-доставку). |

`payload` обов'язковий, якщо ви не скасовуєте доставку. Усе інше — відсутній `return`, рядок, об'єкт без `payload` і без `cancel` — це порушення контракту, і спроба вважається невдалою.

### Мова

Скрипт виконується в суворому режимі, ECMAScript 2023. Це один файл і одна синхронна функція:

- без модулів, без `require`, без `import`, без `module.exports`;
- без `async`, без `await`, без промісів, на які можна було б зачекати;
- без стану між запусками. Кожен запуск отримує чистий глобальний контекст, тож змінна, задана на верхньому рівні, під час наступної доставки знову матиме початкове значення.

`console.log`, `console.info`, `console.warn`, `console.error` і `console.debug` не друкуються, а збираються й показуються поруч із результатом у [«Студії трансформацій»](/docs/uk/outgoing/transform-studio/) — зокрема й ті рядки, які скрипт устиг записати перед тим, як кинути помилку: часто це єдина підказка, яка є.

### Чого скрипт свідомо не може змінити

- **Адресу.** Railhook перевіряє адресу за правилами SSRF *до* того, як запуститься скрипт. Скрипт, який міг би переписати її після цього, стояв би вже по той бік цієї перевірки, — і трансформація перетворилася б на спосіб надіслати ваш підписаний трафік будь-куди. `webhook.url` можна прочитати; присвоєння йому нічого не робить.
- **HTTP-метод.** Спроба — це `POST`, і жодне повернене значення цього не змінює.
- **Секрети.** Власного сховища секретів у скрипта немає. Якщо скрипту треба автентифікуватися в отримувача, для цього є облікові дані самого ендпоінта чи призначення — секрет підпису, клієнтський сертифікат mTLS, налаштування автентифікації призначення. Вони зашифровані в сховищі й застосовуються *після* того, як скрипт відпрацював, тож прочитати чи перезаписати їх він не може.
- **Власні заголовки Railhook.** Спершу лягають заголовки, які повернув скрипт, а вже поверх них — облікові дані та власні заголовки ендпоінта чи призначення; підпис обчислюється взагалі поза цим об'єднанням. Скрипт може додати заголовок, але не видати себе за когось іншого.

## Пісочниця

Скрипт належить одній організації, а виконується на воркерах, спільних для всіх. Тому він отримує мову — і більше нічого: ані файлової системи, ані мережі, ані потоків, ані змоги назвати бодай один Java-клас.

### Обмеження

До кожного запуску застосовують п'ять обмежень. Це налаштування розгортання, а не окремої трансформації, бо захищають вони того, хто утримує воркери. Жодне з них не можна ні підняти, ні перехопити, ні обійти зсередини скрипта.

| Змінна | Типово | Що станеться, якщо вийти за межу |
|---|---|---|
| `TRANSFORM_SCRIPT_TIMEOUT_MS` | `2000` | Запуск зупиняють, спроба невдала з причиною `TIMEOUT`. Це час одного запуску на воркер-потоці, який тим часом більше нічим не зайнятий. |
| `TRANSFORM_SCRIPT_MAX_MEMORY_MB` | `128` | Запуск зупиняють, спроба невдала з причиною `MEMORY`. Рахується те, скільки запуск виділив пам'яті, а не скільки тримає: скрипт, який проганяє через збирач сміття гігабайт, обходиться воркеру так само дорого, як той, що її утримує. |
| `TRANSFORM_SCRIPT_MAX_OUTPUT_BYTES` | `1048576` | Більше тіло запиту не надсилається, а дає невдачу з причиною `OUTPUT_TOO_LARGE`. Отримувач однаково відхилив би його, а так у помилці названо скрипт, а не ендпоінт. |
| `TRANSFORM_SCRIPT_MAX_CONSOLE_LINES` | `100` | Нічого не ламається. Запуск триває далі, зайві рядки відкидаються, і в результаті зазначено, що їх відкинуто. |
| `TRANSFORM_SCRIPT_MAX_CHARS` | `65536` | Скрипт не компілюють, а відхиляють із причиною `SOURCE_TOO_LARGE`. Довший за цю межу API відхиляє ще під час збереження, тож це друга лінія, а не перша. |

Кожне з них живе у вашому `.env` — див. [довідник з конфігурації](/docs/uk/self-hosting/configuration/).

### Що заборонено

Кожен рядок нижче — це тест, а не наміри.

| Спроба | Що станеться |
|---|---|
| `require('fs')`, `readFully('/etc/passwd')`, `load('https://…/evil.js')` | Немає ні файлової системи, ні завантажувача. `require` і `load` не визначені. |
| `fetch(…)`, `new XMLHttpRequest()`, `new java.net.Socket(…)` | Немає мережі. Не заблокований сокет — жодного сокета взагалі. |
| `new Worker('x')` | Скрипт не може створити потік. Він виконується рівно на тому потоці, який його викликав, і не може пережити виклик. |
| `Java.type('java.lang.System')`, `Packages.java.lang.System`, `new java.io.File(…)` | Жодного Java-класу назвати не можна, тож недосяжні ні репозиторій, ні пул з'єднань, ні рядок чужої організації. |
| `process.env`, `Polyglot.eval(…)` | Немає ні середовища хоста, ні другої мови. `process`, `Polyglot`, `java`, `Java`, `load` і їхні сусіди видаляються ще до вашого першого рядка, тож помилка звучить як «не визначено», а не як щось напівробоче. |
| `while (true) {}` | Коли минає тайм-аут, запуск скасовують ззовні, з іншого потоку. |
| `while (true) { a.push(new Array(200000)) }` | Те саме, коли перевищено межу виділеної пам'яті. |

<Aside type="danger" title="Скасування не перехопити через try/catch у скрипті">
Ні тайм-аут, ні межу пам'яті не дотримують, «попросивши» скрипт зупинитися: увесь запуск розбирають ззовні. Тож `while (true)` усередині `try` — і навіть у його `finally` — завершується так само швидко, як і сам по собі. Скрипт, що пішов урознос, коштує одного слота доставки протягом тайм-ауту й нічого більше: наступний скрипт, як і скрипти всіх інших організацій, працює далі.
</Aside>

## Розібраний приклад

Три речі, яких не вміє мова шаблонів: перебудувати масив, додати поле за умовою, відформатувати дату. Саме цей скрипт є тією фікстурою, за якою тести звіряють і попередній перегляд, і воркер, — тож тут написано саме те, що він видає.

```js title="Трансформація"
function handler(webhook) {
  // 1. Reshape an array — a template cannot loop.
  var lines = webhook.payload.items.map(function (item) {
    return { sku: item.sku, total: money(item.qty * item.price) };
  });

  var out = {
    order: webhook.payload.id,
    lines: lines,
    value: money(lines.reduce(function (sum, line) { return sum + line.total; }, 0))
  };

  // 2. Add a field conditionally — a template cannot branch.
  if (out.value >= 100) {
    out.review = 'manual';
  }

  // 3. Format a date — a template cannot compute.
  out.day = new Date(webhook.payload.placed_at).toISOString().slice(0, 10);

  return { payload: out, headers: { 'X-Order-Value': out.value.toFixed(2) } };
}

function money(amount) {
  return Math.round(amount * 100) / 100;
}
```

```json title="Вміст події"
{
  "id": "ord_9001",
  "placed_at": "2026-09-20T14:05:09.123Z",
  "items": [
    { "sku": "WIDGET", "qty": 2, "price": 19.99 },
    { "sku": "GADGET", "qty": 1, "price": 61.5 }
  ]
}
```

```json title="Доставлене тіло запиту"
{
  "order": "ord_9001",
  "lines": [
    { "sku": "WIDGET", "total": 39.98 },
    { "sku": "GADGET", "total": 61.5 }
  ],
  "value": 101.48,
  "review": "manual",
  "day": "2026-09-20"
}
```

І один доданий заголовок: `X-Order-Value: 101.48`.

## До чого підключають трансформацію

Обидва види підключають в однакових місцях, і `kind` мандрує разом із трансформацією.

| До чого | Дія |
|---|---|
| Підписка, `transformationId` | Збережена трансформація, яку застосовують до кожної доставки цієї підписки. |
| Підписка, `payloadTemplate` | Вбудований шаблон; діє, коли `transformationId` не задано. |
| Правило, дія `TRANSFORM` | Замінює трансформацію підписки для подій, які підпадають під правило. Якщо трансформацію задають кілька таких правил, діє останнє. Див. [Правила](/docs/uk/outgoing/rules/). |
| Призначення, `transformationId` | Збережена трансформація, яку застосовують до вхідних вебхуків перед пересиланням. |
| Призначення, `payloadTransform` | Один JSONPath-вираз, наприклад `$.data`; діє, коли `transformationId` не задано. |
| Воркфлоу, вузол `transform` | Змінює структуру даних усередині воркфлоу. Скрипт бачить вхідні дані кроку як свій `payload` і нічого — як контекст доставки, а скрипт, який скасовує, завершує крок невдачею: доставки, яку можна було б скасувати, тут немає. Див. [Воркфлоу](/docs/uk/outgoing/workflows/). |

## Коли трансформація спрацьовує

Трансформацію застосовують у кожній спробі, ще до обчислення підпису. Підпис охоплює вже трансформовані байти, тож отримувач, перевіряючи підпис, перевіряє саме те, що отримав.

Збережену трансформацію Railhook завантажує в момент спроби. Тож якщо виправити зламаний шаблон чи скрипт, це подіє на всі наступні спроби.

<Aside type="danger" title="Через зламану трансформацію оригінальний вміст не витече">
Якщо налаштовану трансформацію не вдається застосувати — шаблон не обчислюється, скрипт кинув помилку, вичерпав тайм-аут чи пам'ять або повернув не ту структуру — або `transformationId` вказує на відсутню чи вимкнену трансформацію, спроба вважається невдалою, і Railhook повторює її, як і будь-яку іншу невдачу. Оригінальний вміст замість трансформованого ніколи не надсилається, бо саме трансформаціями часто вирізають персональні дані, перш ніж ті залишать систему. Кожна невдача збільшує лічильник `transform_failed_total`.
</Aside>

### Чому скрипт не спрацював

Невдалий скрипт записують у спробу як `TRANSFORM_FAILED` — із причиною і, якщо вона відома, з номером рядка у вашому власному скрипті, відлік якого починається з вашого першого рядка, а не з того, що Railhook додає навколо нього.

| Причина | Що це означає |
|---|---|
| `SYNTAX` | Скрипт не скомпілювався. |
| `CONTRACT` | Скрипт скомпілювався, але не оголошує `handler` або повернув не той конверт. |
| `RUNTIME` | Скрипт виконався й кинув помилку або звернувся до того, чого в пісочниці немає. |
| `TIMEOUT` | Скрипт ще виконувався, коли вичерпався час. |
| `MEMORY` | Скрипт виділив більше пам'яті, ніж дозволено. |
| `OUTPUT_TOO_LARGE` | Скрипт повернув тіло запиту більше за дозволене. |
| `SOURCE_TOO_LARGE` | Сам скрипт довший, ніж рушій погоджується компілювати. |
| `UNAVAILABLE` | Рушія немає в цьому розгортанні. Це проблема того, хто його утримує, а не автора скрипта. |

### Коли скрипт скасовує доставку

`{ cancel: true }` — це не невдача, і поводяться з нею не так, як з усім іншим:

- нічого не надсилається — ендпоінт узагалі не запитують, тож його circuit breaker це ніяк не зачіпає;
- нічого не повторюється — наступна спроба прогнала б той самий скрипт на тому самому вмісті й дійшла б того самого висновку;
- доставка на цьому завершується зі статусом **`CANCELLED`**, який не є ні `SUCCESS`, ні `FAILED`, і записується як `CANCELLED_BY_TRANSFORMATION`, а далі — причина, яку назвав скрипт, або `no reason given`;
- доставка **не** потрапляє до [«Недоставлених повідомлень»](/docs/uk/outgoing/retries/). Та черга — для того, що людина ще може полагодити, а фільтр, який робить свою роботу, — це не той випадок;
- її рахує лічильник `transform_cancelled_total`, окремо від `transform_failed_total`.

Беріть це для трафіку, якого отримувач не має бачити взагалі: тестові події, клієнт, який відмовився від розсилки, тип події, у якому, як виявилося, нема чого надсилати.

```js
function handler(webhook) {
  if (webhook.payload.livemode === false) {
    return { cancel: true, cancelReason: 'test traffic' };
  }
  return { payload: webhook.payload };
}
```

## Як створити й перевірити трансформацію

<Steps>

1. Створіть її. Поля `name` і `template` обов'язкові; у `template` лежить або JSON-шаблон, або скрипт, і воно може мати до 65 536 символів. Якщо `kind` не задано, це `TEMPLATE`.

   ```bash
   curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/transformations" \
     -H "X-API-Key: $API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"name":"Orders to CRM","kind":"JAVASCRIPT","template":"function handler(webhook) { return { payload: { id: webhook.payload.orderId } }; }"}'
   ```

   Перед збереженням скрипт компілюють і перевіряють, чи є в ньому `handler`, — у тій самій пісочниці й з тими самими обмеженнями, які має справжня доставка. Тож синтаксичну помилку відхиляють саме тут, із номером рядка, а не щоразу на кожній спробі.

2. Перевірте результат на вставленому вмісті через `POST /api/v1/projects/{projectId}/transform-preview`. Надішліть `inputPayload` і або `transformationId`, або вбудований `template` разом із його `kind`. Для скрипта можна додати ще `eventType`, `eventId`, `url` і `customHeaders` — саме їх він побачить у `webhook.*`. У відповіді буде результат, заголовки, усе записане в `console`, тривалість запуску, а в разі невдачі — причина й рядок. Нічого не доставляється.

3. Змоделюйте доставку (пробний запуск) через `POST /api/v1/projects/{projectId}/transform-preview/delivery-dry-run`. Надішліть `payload`, трансформацію або `payloadTemplate`, а також `endpointId`. У відповіді буде трансформоване тіло, заголовки й підпис, які було б надіслано, а також назва й версія трансформації. Нічого не надсилається.

4. Підключіть трансформацію, задавши `transformationId` у підписці.

</Steps>

## У панелі керування

[«Студія трансформацій»](/docs/uk/outgoing/transform-studio/) — це **«Розробка» → «Студія трансформацій»**, а також кнопка редагування на самій трансформації. Вона виконує рівно той самий рушій, що й воркер, з тією самою пісочницею й тими самими обмеженнями, тож скрипт, який працює там, працює й на доставці. Студія має вкладки **«Вхід»**, **«Вихід»**, **«Різниця»** і **«Консоль»**, запускається на ⌘/Ctrl+Enter, підсвічує рядок, на якому сталася невдача, і зберігає скрипт назад у трансформацію — а це публікує нову версію, так само як збереження через API.

## Історія версій

Збереження шаблону чи скрипта, який відрізняється від збереженого раніше, публікує нову версію і збільшує номер версії. Збереження без зміни тексту — перейменування трансформації, редагування опису, вимкнення — номер версії не чіпає. Зміна виду (`kind`) без жодної правки тексту теж рахується зміною, бо той самий текст означає різне в двох мовах.

Кожну опубліковану версію збережено разом із текстом, **мовою, якою її написано**, автором і часом публікації. У панелі номер версії у списку трансформацій відкриває історію: там можна прочитати будь-яку версію, позначити дві й побачити, що між ними змінилося, та повернути одну з них. API дає те саме під самою трансформацією — див. [Довідник API](/docs/uk/api-reference/).

Відновлення — це не скасування. Воно публікує стару версію як наступну й лишає все опубліковане пізніше на місці, щоб запис про те, яка версія працювала в певний момент, залишався правдивим. Нова версія позначена версією, з якої її відновлено, а саме відновлення потрапляє до журналу аудиту як `RESTORE`. Відновлення повертає текст **і** мову разом — інакше відновлення версії-шаблону в трансформацію, яку відтоді переписали як скрипт, лишило б JSON у трансформації, позначеній як `JAVASCRIPT`, і кожна спроба падала б, намагаючись його скомпілювати.

```bash
curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/transformations/$TRANSFORMATION_ID/versions/2/restore" \
  -H "X-API-Key: $API_KEY"
```

<Aside type="tip" title="Два скрипти порівнюють рядок за рядком">
Порівняння поле за полем можна зробити для двох JSON-шаблонів і не можна — для двох скриптів, де кожен рядок читався б як одне поле, яке не розбирається. Якщо хоч одна зі сторін порівняння — JavaScript, порівняння за полями порожнє, а натомість два тексти порівнюють рядок за рядком — і саме цього й хоче людина, яка читає скрипт.
</Aside>

<Aside type="caution" title="Історія обмежена">
Кожна трансформація зберігає останні `TRANSFORMATION_HISTORY_LIMIT` версій — типово 50. Старіші за них зникають; версія, яка зараз працює, не зникає ніколи. Якщо потрібно сягати далі в минуле, збільште значення у своєму `.env` — до 65536 символів на версію.
</Aside>

Трансформації, які існували до появи історії, починають з однієї версії — того шаблону, який мають зараз.
