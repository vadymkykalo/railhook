**Ендпоінт** — це URL, який готовий приймати ваші події. **Підписка** визначає, які типи подій цей ендпоінт хоче отримувати. Коли ваша система надсилає подію, Railhook створює по одній **доставці** на кожен ендпоінт із відповідною підпискою і займається кожною доставкою, доки вона не пройде успішно або Railhook її не полишить.

У панелі ендпоінт разом із його підписками показано як одне **з'єднання** на екрані «З'єднання». Це лише спосіб показу, а не окремий запис: змінюючи з'єднання, ви змінюєте ендпоінт або його підписки.

У прикладах нижче `$RAILHOOK_URL` — адреса вашого API Railhook, `$PROJECT_ID` — ваш проєкт, а `$API_KEY` — API-ключ проєкту.

## Як створити ендпоінт і підписати його

<Steps>

1. Створіть ендпоінт.

   ```bash
   curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/endpoints" \
     -H "X-API-Key: $API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"url":"https://api.customer.com/webhooks","description":"Orders"}'
   ```

   Відповідь містить `secret` і `standardWebhooksSecret`. Збережіть їх одразу: у відкритому вигляді API повертає секрет лише під час створення ендпоінта та ротації його секрету.

2. Підпишіть ендпоінт на тип події.

   ```bash
   curl -X POST "$RAILHOOK_URL/api/v1/projects/$PROJECT_ID/subscriptions" \
     -H "X-API-Key: $API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"endpointId":"'"$ENDPOINT_ID"'","eventType":"order.completed"}'
   ```

3. Надішліть подію (див. [Надіслати подію](#надіслати-подію) нижче). Кожен ендпоінт, підписаний на `order.completed`, отримає власну доставку.

</Steps>

### Поля ендпоінта

| Поле | Що робить |
|---|---|
| `url` | Обов'язкове. Адреса, на яку надсилаються доставки. Перевіряється на належність до приватних діапазонів адрес, див. [Безпека ендпоінта](/docs/uk/outgoing/endpoint-security/). |
| `description` | Довільний текст, до 500 символів. |
| `enabled` | Чи отримує ендпоінт доставки. |
| `autoDisabledAt` | Лише для читання. Проставляється, коли Railhook вимкнув ендпоінт сам, див. [Коли Railhook вимикає ендпоінт](#коли-railhook-вимикає-ендпоінт). Відсутнє, якщо вимкнули ви. |
| `autoDisabledReason` | Лише для читання. Причина, словами. |
| `failingSince` | Лише для читання. Початок поточної безперервної серії невдалих доставок; зникає, щойно одна вдасться. |
| `signatureScheme` | `BOTH` (типово), `LEGACY` або `STANDARD`: які заголовки підпису надсилаються. Див. [Перевірка підписів](/docs/uk/outgoing/signatures/). |
| `rateLimitPerSecond` | Ліміт доставок на секунду для цього ендпоінта, від 0 до 10 000. `0` знімає ліміт. |
| `secret` | Необов'язкове. Ваш власний секрет підпису замість згенерованого. |
| `allowedSourceIps` | Поле для нотатки. Нічого не обмежує, див. [Безпека ендпоінта](/docs/uk/outgoing/endpoint-security/#дозволені-ip-адреси-джерела). |

## Коли Railhook вимикає ендпоінт

Отримувач, мертвий уже кілька днів, раніше й далі витрачав увесь бюджет повторних спроб: кожна нова подія починала розклад спочатку, і ніщо не казало, що проблема в самому ендпоінті. Тепер Railhook вимикає такий ендпоінт і повідомляє вас.

Правило — дві умови, і мають виконатися обидві:

| Умова | Типово | Змінна |
|---|---|---|
| Жодної успішної доставки протягом | 72 години | `ENDPOINT_AUTO_DISABLE_AFTER_HOURS` |
| …і в цій серії щонайменше стільки невдалих спроб | 10 | `ENDPOINT_AUTO_DISABLE_MIN_FAILURES` |

Друга умова потрібна, щоб ендпоінт, який отримує одну подію на тиждень, не вимкнули просто за бездіяльність. Одна успішна доставка в будь-який момент обнуляє і серію, і лічильник.

У списку ендпоінтів і в рядку на сторінці «З'єднання» видно **«Вимкнено автоматично»** та відколи. API повертає на ендпоінті `autoDisabledAt`, `autoDisabledReason` і `failingSince`.

### Що стається з уже поставленими в чергу доставками

Вони **не** зникають і не завершуються тихо невдачею. Усе, що вже було адресовано ендпоінту, потрапляє в «Недоставлені повідомлення» із записаною причиною — тож коли отримувач запрацює, все це можна повторити. Див. [Повторні спроби та недоставлені повідомлення](/docs/uk/outgoing/retries/).

Це навмисно відрізняється від ендпоінта, який вимикаєте *ви*: там доставки в черзі завершуються як `FAILED`. Вимкнути ендпоінт — це сказати, що ви більше не хочете туди доставляти; Railhook вимикає його, коли доставити не вдалося.

### Як увімкнути назад

Повторне ввімкнення знімає автоматичне вимкнення разом із серією невдач, тож наступний прохід не вимкне ендпоінт одразу знову. Скористайтеся кнопкою живлення на ендпоінті або `POST /api/v1/projects/{projectId}/endpoints/{id}/enable`. Спершу полагодьте отримувача: ендпоінт, увімкнений, поки він ще падає, просто почне нову серію.

### Кого сповіщають

Сповіщення з'являється на сторінці «Сповіщення» проєкту, а якщо в розгортанні налаштована пошта (`EMAIL_ENABLED=true`) — один лист іде власникам організації: який саме ендпоінт, відколи він падає і як увімкнути його назад. Правило сповіщень для цього не потрібне: Railhook повідомляє про власне рішення.

### Вхідні призначення

Призначення, яке падає так само довго, вимикається на тих самих умовах, а його пересилання в черзі так само потрапляють у «Недоставлені пересилання».

### Як вимкнути цю поведінку

`ENDPOINT_AUTO_DISABLE_ENABLED=false` і в api, і у воркері. Тоді нічого не підраховується і нічого не вимикається автоматично.

<Aside type="caution" title="Нові ендпоінти й перевірка">
Типово новий ендпоінт отримує статус `SKIPPED` і одразу приймає доставки. Якщо оператор задав `WEBHOOK_ENDPOINT_VERIFICATION_REQUIRED=true`, новий ендпоінт отримує статус `PENDING`, і кожна доставка на нього завершується невдачею, доки він не пройде перевірку власника. Див. [Безпека ендпоінта](/docs/uk/outgoing/endpoint-security/#доведіть-що-ендпоінт-ваш).
</Aside>

### Поля підписки

| Поле | Що робить |
|---|---|
| `endpointId` | Обов'язкове. Ендпоінт, який отримує події, що підпадають під підписку. |
| `eventType` | Обов'язкове. Точний тип події або шаблон, див. нижче. |
| `enabled` | Чи створює підписка доставки. |
| `orderingEnabled` | Доставляти події цього ендпоінта в порядку їх створення. Типово вимкнено, див. [Порядок доставки](/docs/uk/outgoing/ordering/). |
| `maxAttempts` | Від 1 до 20. Скільки спроб зробити, перш ніж полишити доставку. |
| `retryableStatuses` | Які HTTP-статуси варті ще однієї спроби, напр. `408,429,500-599` або `5xx,!501`. Див. [Які статуси варті повтору](/docs/uk/outgoing/retries/#які-статуси-варті-повтору). |
| `retryDelays` | Інтервали між спробами в секундах через кому, наприклад `60,300,900`. |
| `timeoutSeconds` | Від 1 до 60, типово 30. Скільки одна спроба чекає на відповідь. |
| `transformationId` | Збережена трансформація, яку треба застосувати, див. [Трансформації](/docs/uk/outgoing/transformations/). |
| `payloadTemplate` | Вбудований шаблон; діє, коли `transformationId` не задано. |
| `customHeaders` | Додаткові HTTP-заголовки як JSON-об'єкт у рядку. |

Якщо не вказати `maxAttempts` і `retryDelays`, діятиме типовий розклад повторних спроб для вихідних вебхуків, див. [Повторні спроби та недоставлені повідомлення](/docs/uk/outgoing/retries/).

### Шаблони типів подій

Тип події пишуть малими літерами, він починається з літери, а сегменти в ньому розділено крапками: `order.completed`. Підписка може вказувати не на один тип, а на шаблон:

| Шаблон | Під нього підпадає |
|---|---|
| `order.completed` | Лише цей тип події. |
| `order.*` | Рівно один сегмент після `order.`: `order.completed`, `order.updated`. Але не `order.line.added`. |
| `order.**` | Будь-яка кількість сегментів після `order.`: `order.completed`, `order.line.added`. |
| `*` | Будь-який тип події з одного сегмента. |
| `**` | Усі типи подій у проєкті. |

## Надіслати подію

Надішліть `POST /api/v1/events` із полем `type` та об'єктом `data`. У відповідь прийде `201`. Додавайте заголовок `Idempotency-Key`, щоб отримувач міг розпізнати дублікат.

<Tabs syncKey="lang">
<TabItem label="Node.js">

```ts
import { Railhook } from '@railhook/node';

const client = new Railhook({
  apiKey: process.env.RAILHOOK_API_KEY,
  baseUrl: process.env.RAILHOOK_URL,
});

const event = await client.events.send(
  { type: 'order.completed', data: { orderId: 'ord_12345', amount: 99.99 } },
  'order-12345-completed',
);
```

</TabItem>
<TabItem label="Python">

```python
import os

from railhook import Railhook, Event

client = Railhook(
    api_key=os.environ["RAILHOOK_API_KEY"],
    base_url=os.environ["RAILHOOK_URL"],
)

event = client.events.send(
    Event(type="order.completed", data={"order_id": "ord_12345", "amount": 99.99}),
    idempotency_key="order-12345-completed",
)
```

</TabItem>
<TabItem label="PHP">

```php
<?php
use Railhook\Railhook;

$client = new Railhook(
    apiKey: getenv('RAILHOOK_API_KEY'),
    baseUrl: getenv('RAILHOOK_URL'),
);

$event = $client->events->send(
    type: 'order.completed',
    data: ['orderId' => 'ord_12345', 'amount' => 99.99],
    idempotencyKey: 'order-12345-completed',
);
```

</TabItem>
<TabItem label="cURL">

```bash
curl -X POST "$RAILHOOK_URL/api/v1/events" \
  -H "X-API-Key: $API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-12345-completed" \
  -d '{"type":"order.completed","data":{"orderId":"ord_12345","amount":99.99}}'
```

</TabItem>
</Tabs>

### Політика ідемпотентності

Що станеться з подією, надісланою без `Idempotency-Key`, вирішує налаштування проєкту `idempotencyPolicy`:

| Політика | Подія без ключа |
|---|---|
| `NONE` | Приймається, ключ не генерується. |
| `AUTO` | Приймається й отримує випадковий ключ. |
| `REQUIRED` | Відхиляється. |

За будь-якої політики, якщо надіслати ключ, який у проєкті вже використано, Railhook поверне первісну подію, а не створить другу.

## Що надходить на ендпоінт

Тілом запиту на ендпоінт є сам об'єкт `data` події, без обгортки. Ідентифікатори передаються в заголовках:

```http title="Доставка"
POST /webhooks HTTP/1.1
Content-Type: application/json
X-Signature: t=1738000000000,v1=<hex hmac-sha256>
X-Timestamp: 1738000000000
X-Event-Id: 6f0e…
X-Delivery-Id: 91ab…
X-Sequence-Number: 0
Idempotency-Key: order-12345-completed-<endpoint-id>
webhook-id: 91ab…
webhook-timestamp: 1738000000
webhook-signature: v1,<base64>

{"orderId":"ord_12345","amount":99.99}
```

Типу події в тілі немає. Розрізняйте події за вмістом або за ендпоінтом чи задайте підписці шаблон, який додає `type` у тіло.

`Idempotency-Key` складається з ключа події, `-` та ідентифікатора ендпоінта. Якщо в події немає ключа, замість нього береться ідентифікатор події. Цей заголовок однаковий в усіх спробах доставки.

<Aside type="tip">
Щоб перевірити, чи ендпоінт відповідає, ще до того, як на нього піде реальний трафік, скористайтеся `POST /api/v1/projects/{projectId}/endpoints/{id}/test`. У відповіді буде видно, чи запит пройшов успішно, HTTP-статус і затримку. Повні формати запитів і відповідей — у [довіднику API](/docs/uk/api-reference/).
</Aside>
