Railhook надає перевірки стану на публічному порту, а метрики Prometheus — на внутрішніх. У репозиторії є необов'язковий стек моніторингу — Grafana, Prometheus, Alertmanager, Loki та експортери для хоста, контейнерів і доступності, — який можна запустити поруч однією командою Compose.

## Перевірки стану

`RAILHOOK_URL` — адреса вашого інстансу: `http://localhost` після типового встановлення, `http://localhost:<port>`, якщо ви передали `--port`, або `https://<your domain>`, якщо встановлювали з `--domain`.

```bash
curl -f "$RAILHOOK_URL/actuator/health/liveness"
curl -f "$RAILHOOK_URL/actuator/health/readiness"
```

nginx проксує лише шляхи перевірок стану. Будь-який інший шлях `/actuator/` на публічному порту відповідає `404`.

## Метрики

Метрики доступні на окремих портах керування (management) лише всередині мережі Docker і не потребують облікових даних:

| Сервіс | Адреса метрик |
|---|---|
| API | `http://api:8082/actuator/prometheus` |
| Воркер | `http://worker:8081/actuator/prometheus` |

На публічний порт їх навмисно не проксовано: метрики розкрили б назви ендпоінтів і обсяги трафіку будь-кому, хто їх запросить.

Обидва сервіси публікують їх завжди, незалежно від того, чи запущено вбудований стек, тож ці порти може опитувати будь-який наявний у вас Prometheus: бакети затримок HTTP-запитів, метрики клієнтів Kafka та лічильники прийнятих подій, створених доставок, спрацювань правил і очищення застарілих даних. Кількість значень міток обмежена — жодних ідентифікаторів організацій, проєктів чи ендпоінтів.

## Вбудований стек

`monitoring/` у репозиторії — другий Compose-проєкт: Grafana, Prometheus, Alertmanager, Loki і Promtail, node-exporter, cAdvisor та blackbox-exporter. Він вимкнений, доки ви його не запустите, а його ліміти пам'яті в сумі становлять 1,5 ГБ.

Порт публікує лише Grafana, на `127.0.0.1:3001`. Prometheus, Alertmanager і Loki доступні лише всередині мережі стека; сторінки Explore та Alerting у Grafana читають усі три.

### На сервері, встановленому через install.sh

<Steps>

1. **Задайте пароль Grafana.** Типового пароля немає: Grafana не стартує без нього або з паролем, коротшим за 16 символів.

   ```bash
   cd /opt/railhook
   echo "GRAFANA_ADMIN_PASSWORD=$(openssl rand -base64 24)" >> .env
   ```

2. **Вкажіть, куди йдуть сповіщення.** Листи надсилаються через той самий SMTP-релей, яким уже користується платформа (`EMAIL_FROM`, `SMTP_*`), якщо ви не задали змінні `ALERTMANAGER_SMTP_*`. Кожен лист містить посилання на Grafana за адресою `MONITORING_DOMAIN`; якщо домену немає, лист пояснює, як відкрити Grafana через SSH-тунель.

   ```bash
   echo "ALERTMANAGER_EMAIL_TO=you@example.com" >> .env
   ```

   Slack (`ALERTMANAGER_SLACK_WEBHOOK_URL`), довільний вебхук (`ALERTMANAGER_WEBHOOK_URL`) і Telegram (`ALERTMANAGER_TELEGRAM_BOT_TOKEN`, `ALERTMANAGER_TELEGRAM_CHAT_ID`) налаштовуються так само.

3. **Завантажте `monitoring/` для релізу, на якому працює сервер, і запустіть стек.** Це окремий Compose-проєкт `railhook-monitoring`, який читає `.env` платформи:

   ```bash
   v=$(grep '^API_IMAGE_TAG=' .env | cut -d= -f2)
   curl -fsSL "https://github.com/vadymkykalo/railhook/archive/refs/tags/v${v}.tar.gz" \
     | tar xz --strip-components=1 --wildcards '*/monitoring/*'
   docker compose -p railhook-monitoring --env-file .env -f monitoring/docker-compose.yml up -d
   ```

   Стек приєднується до мережі платформи: `railhook_webhook-network`, якщо каталог встановлення називається `railhook`. Для будь-якого іншого каталогу задайте в `.env` змінну `RAILHOOK_NETWORK` з назвою, яку показує `docker network ls`. Задайте `MONITORING_NODENAME` — ім'я сервера для дашборду Host.

   Після `./railhook upgrade` знову завантажте `monitoring/` для нового релізу й виконайте той самий `up -d` з `--force-recreate`. Контейнери монтують файли, з якими стартували, тож без цього прапорця лишаються на старих правилах і дашбордах.

4. **Відкрийте Grafana** через SSH-тунель і увійдіть як `admin` з паролем із `.env`:

   ```bash
   ssh -L 3001:127.0.0.1:3001 root@your-server
   ```

   Потім відкрийте `http://localhost:3001`.

</Steps>

Та сама команда з `ps`, `logs -f [service]` або `down` замість `up -d` показує контейнери, показує логи в реальному часі або зупиняє стек. `down` зберігає метрики та логи в томах `railhook-monitoring_*`.

### Grafana на власному домені

Задайте `MONITORING_DOMAIN=grafana.example.com` у `.env`, спрямуйте це доменне ім'я на сервер і перезапишіть Caddyfile через `--refresh` інсталятора:

```bash
curl -fsSL https://railhook.io/install.sh | bash -s -- --refresh --dir /opt/railhook
```

Він додасть ім'я до Caddyfile і перезавантажить Caddy, який отримає сертифікат так само, як для платформи. `./railhook upgrade` цей блок зберігає. Якщо ви встановлювали з `--behind-proxy`, натомість спрямуйте на `127.0.0.1:3001` власний проксі.

<Aside type="caution">
Поставте перед цим доменом identity-aware проксі, наприклад Cloudflare Access. Вхід у Grafana не має бути єдиним бар'єром між інтернетом і вашими логами. Якщо проксі охоплює всі шляхи, виключіть `/.well-known/acme-challenge/`, інакше Caddy не зможе оновити сертифікат.

Деякі проксі взагалі не пускають Let's Encrypt до цього імені: Cloudflare з Always Use HTTPS перенаправляє ACME-перевірку на HTTPS, де сертифіката ще немає. Тоді дайте Caddy готовий сертифікат, наприклад origin-сертифікат Cloudflare для цього імені. Скопіюйте сертифікат і ключ у том даних Caddy, вкажіть їх у `.env` і знову виконайте `--refresh`, наведений вище:

```bash
docker exec webhook-caddy mkdir -p /data/certs
docker cp grafana.pem webhook-caddy:/data/certs/grafana.example.com.pem
docker cp grafana.key webhook-caddy:/data/certs/grafana.example.com.key
printf '%s\n' MONITORING_TLS_CERT=/data/certs/grafana.example.com.pem \
  MONITORING_TLS_KEY=/data/certs/grafana.example.com.key >> .env
```
</Aside>

### З клону

<Steps>

1. Запустіть Railhook командою `make up`, потім додайте `GRAFANA_ADMIN_PASSWORD` до `.env`.

2. Запустіть стек:

   ```bash
   make monitoring-up
   ```

3. Відкрийте Grafana на `http://localhost:3001`.

</Steps>

`make monitoring-down` зупиняє стек; `make monitoring-logs` показує його логи в реальному часі.

### Дашборди

| Дашборд | Що показує |
|---|---|
| Railhook — Overview | Чи доступний публічний сайт, активні сповіщення, диск, пам'ять, CPU і вік резервної копії, далі — події, доставки, черги та DLQ |
| Alerts | Усі активні й очікувані сповіщення, чи працює сам ланцюжок сповіщень, історія сповіщень і посилання, щоб приглушити будь-яке з них |
| Errors | Рядки логів з помилками й попередженнями за сервісами, найчастіші повідомлення про помилки, 4xx і 5xx в API та nginx, 401/403/429, невдалі доставки та зростання DLQ |
| Logs | Рядки логів API, воркера, nginx інтерфейсу, Caddy, Postgres і резервного копіювання з фільтрами за сервісом, рівнем, текстом, correlation ID або organization ID |
| Host | Node Exporter Full: CPU, пам'ять, диски, мережа, файлові системи |
| Containers | CPU, пам'ять відносно ліміту Compose, мережа й перезапуски для кожного контейнера |
| Uptime | Стан перевірок, доступність за період, час відповіді, скільки днів лишилося сертифікату TLS, резервні копії |
| Worker & Circuit Breaker, JVM & Micrometer, Kafka | Внутрішня робота платформи |

### Які сповіщення надсилає

Правила для платформи — той самий набір, що входить у Helm-чарт. Крім них, для самого сервера є такі:

| Сповіщення | Спрацьовує, коли |
|---|---|
| `HostDiskAlmostFull`, `HostDiskCritical` | Файлова система заповнена більш ніж на 85% або більш ніж на 95% |
| `HostMemoryHigh`, `HostOomKill` | Пам'ять зайнята більш ніж на 90% протягом 10 хвилин або ядро вбило процес |
| `HostLoadHigh` | 15-хвилинне навантаження перевищує кількість CPU в 1,5 раза |
| `ContainerRestarting`, `ContainerOomKilled`, `ContainerMemoryNearLimit` | Контейнер двічі перезапустився за 15 хвилин, досяг ліміту пам'яті або перевищує 90% від нього |
| `PublicEndpointDown`, `PublicEndpointSlow` | Публічний URL не відповідає ззовні або відповідає довше за 3 секунди |
| `UiDown`, `CaddyDown` | nginx інтерфейсу або Caddy перестає відповідати всередині мережі |
| `TlsCertificateExpiringSoon`, `TlsCertificateExpiryImminent` | Сертифікат спливає менш ніж за 14 днів або менш ніж за 3 |
| `ErrorLogSpike`, `EdgeServerErrorSpike` | Сервіс пише в лог понад 10 помилок на хвилину або nginx віддає понад 5 відповідей 5xx на хвилину |
| `BackupStale`, `BackupMissing` | Найновіша планова резервна копія старша за 26 годин або її немає |
| `Watchdog` | Завжди. Надсилається лише на `ALERTMANAGER_HEARTBEAT_URL` |

Перевірки запитують `https://RAILHOOK_DOMAIN/`, `/docs/` і `/actuator/health`; щоб перевіряти інші адреси, задайте `MONITORING_PROBE_URLS`.

<Aside type="tip">
Будь-яке інше сповіщення надсилає той самий сервер, який воно описує, тож жодне з них не повідомить вам, що цей сервер ліг. Спрямуйте `ALERTMANAGER_HEARTBEAT_URL` на heartbeat-сервіс, наприклад healthchecks.io: він щохвилини отримує `Watchdog` і сповіщає вас, коли той перестає надходити.
</Aside>

Стек знаходить мережу Docker платформи за її міткою Compose. Якщо він вибрав не ту мережу, задайте `RAILHOOK_NETWORK`. Усі змінні — у [довіднику конфігурації](/docs/uk/self-hosting/configuration/).

## На що ставити сповіщення

| Метрика | Чому |
|---|---|
| `delivery_oldest_pending_age_seconds` | Вік найстарішої незавершеної доставки. Хоч би що пішло не так, це видно тут. `forward_oldest_pending_age_seconds` — вхідний відповідник |
| `webhook_dlq_depth`, `incoming_forward_dlq_depth` | Доставки й пересилання, у яких закінчилися повторні спроби і які потребують уваги людини |
| `outbox_oldest_pending_age_seconds` | Прийняті події, які ще не дійшли до Kafka |
| `circuit_breaker_degraded_total` | Redis був недоступний, і circuit breaker пропускав виклики без захисту |

## Kubernetes

Увімкніть інтеграції чарта з kube-prometheus-stack:

```yaml title="values.yaml"
monitoring:
  serviceMonitor:
    enabled: true
  prometheusRule:
    enabled: true
  grafanaDashboards:
    enabled: true
```

ServiceMonitor збирає метрики з порту `management` API та воркера.
