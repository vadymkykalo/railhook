Railhook налаштовується змінними середовища у файлі `.env` поруч із `docker-compose.yml`. Якщо змінну не задано, діє типове значення, вбудоване в Compose-файл. Після зміни `.env` виконайте `./railhook up -d`: Compose перестворить лише ті сервіси, чиї налаштування змінилися.

## Що треба визначити

Майже кожна змінна — це тайм-аут або розмір пакета з цілком придатним типовим значенням. Винятки наведено нижче: їхні типові значення підібрано для розробки, і вони стають неправильними, щойно до інстансу можна дістатися ззовні.

| Змінна | Чому це важливо |
|---|---|
| `APP_ENV` | Зі значенням `production` API відмовляється запускатися з небезпечною конфігурацією, замість того щоб із нею працювати |
| `WEBHOOK_ENCRYPTION_KEY`, `WEBHOOK_ENCRYPTION_SALT` | Шифрують кожен секрет ендпоінта в базі даних. Зробіть їх резервну копію. Ніколи не змінюйте сіль, якщо в базі вже є дані |
| `JWT_SECRET` | Підписує сесії входу |
| `POSTGRES_PASSWORD`, `DB_PASSWORD` | Перша створює користувача бази даних, а з другою підключаються API та воркер. Значення мають збігатися |
| `REDIS_PASSWORD` | Захищає кеш |
| `APP_BASE_URL` | URL, який користувачі вводять у браузері. З нього будуються посилання для підтвердження адреси, запрошень і скидання пароля |
| `CORS_ALLOWED_ORIGINS` | Має містити origin, з якого відкривається панель керування, інакше вхід завершиться помилкою «Invalid CORS request» |
| `TUNNEL_INGRESS_BASE_URL` | Публічна базова адреса для ingress-адрес джерел і адрес тунелів CLI. Якщо змінну не задано, використовується `APP_BASE_URL` |
| `EMAIL_ENABLED`, `EMAIL_FROM`, `SMTP_*` | Якщо пошту вимкнено, облікові записи створюються вже підтвердженими, а запрошення надсилати не можна |
| `RAILHOOK_PORT`, `RAILHOOK_BIND` | Де слухає єдиний опублікований порт |
| `WEBHOOK_TRUSTED_PROXIES` | Проксі, заголовку `X-Forwarded-For` яких Railhook довіряє. Порожнє значення — не довіряти нікому |
| `WEBHOOK_ALLOW_PRIVATE_IPS`, `WEBHOOK_ALLOWED_HOSTS` | Не знімайте блокування приватних адрес. Щоб дозволити лише один внутрішній хост, додайте його назву до списку |
| `DB_HOST` і `COMPOSE_PROFILES` | Щоб використовувати керовану PostgreSQL, задайте змінні `DB_*` і приберіть `embedded-db` із профілів |
| `PLATFORM_ADMIN_TOKEN` | Відкриває доступ до операторських ендпоінтів. Якщо значення порожнє, вони недоступні |
| `API_REPLICAS` | `2` робить оновлення безшовними ціною ще приблизно 600 МБ |

<Aside type="caution">
Змінні з префіксом `VITE_` вбудовуються в панель керування під час збирання її образу. В опублікованих образах їх уже не змінити. Щоб змінити таку змінну, доведеться зібрати власний образ `ui`.
</Aside>

## Листи для нових облікових записів

`ONBOARDING_EMAILS_ENABLED` вмикає два листи для нових облікових записів: привітальний — щойно адресу підтверджено, і одне нагадування через два дні, якщо організація облікового запису досі не надіслала й не отримала жодної події. Кожен лист надсилається не більше одного разу на обліковий запис, відповіді йдуть на `EMAIL_SUPPORT_ADDRESS`, і нічого не надсилається, якщо не ввімкнено також `EMAIL_ENABLED`. Облікові записи, створені до оновлення, у якому з'явилося це налаштування, не отримають жодного з цих листів.

На власному інстансі не вмикайте це налаштування. Обидва листи написав від першої особи автор Railhook для Railhook Cloud, а ваші користувачі реєструвалися не в нього.

## Блог

`BLOG_ENABLED` вмикає `/blog`, його дописи та стрічку. Образ містить їх лише тому, що railhook.io працює на тому самому образі, що й ваш інстанс: це власні статті Railhook, а не вашого сайту.

За замовчуванням блог вимкнено, і вмикає його лише railhook.io. Коли він вимкнений, `/blog` і все під ним відповідають 404, у шапці й підвалі немає посилання на блог, а `/sitemap.xml` не містить жодного допису. UI-контейнер читає це налаштування під час запуску, тож щоб його змінити, достатньо `docker compose up -d ui`, без перезбирання. У Kubernetes це налаштування `ui.publicBlog`.
